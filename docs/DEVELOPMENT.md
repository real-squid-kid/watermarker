# Разработка

Целевая платформа — Windows 11 x64, .NET 10, WPF. SDK выбирается через
[`global.json`](../global.json) с обновлениями внутри установленной feature band
([правила выбора SDK](https://learn.microsoft.com/en-us/dotnet/core/tools/global-json)).

## Подготовка

Из корня репозитория в PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Test-Environment.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Verify.ps1
. ./scripts/Initialize-DotNet.ps1
dotnet run --project src/WaterMarker.App
```

Для проверки обязательных зависимостей видео добавьте `-RequireVideo` к
`Test-Environment.ps1`. Скрипты размещают кэш NuGet и служебные файлы CLI внутри
репозитория в игнорируемых каталогах. Не нужны администраторские права или workloads.
Пакеты из NuGet добавляются по мере реализации соответствующего модуля.

Для ручной проверки на изолированной базе используйте:

```powershell
dotnet run --project src/WaterMarker.App -- --data-directory .local/acceptance/manual
```

Без этого параметра приложение использует профиль Windows. Автоматические тесты
создают собственные временные базы и не затрагивают пользовательскую историю.

Для получения визуальной матрицы критерия 1.9 задайте каталог результатов и путь к
локальной фотографии, затем выполните проверки:

```powershell
$env:WATERMARKER_ACCEPTANCE_DIR = Join-Path (Get-Location) '.local/acceptance/images'
$env:WATERMARKER_PHOTO_FIXTURE = 'C:\path\to\photo.jpg'
./scripts/Verify.ps1
```

Тест сохраняет светлые и тёмные кадры с мелким текстом, фотографию, варианты метки
без проекта и с длинным названием, пять обрезок каждого результата и `coverage.csv`.
Геометрическое покрытие проверяется автоматически; читаемость проверяется визуально.

Для проверок этапа 2 и сохранения макетов окна при 100%, 125% и 150%:

```powershell
$env:WATERMARKER_STAGE2_ARTIFACTS = Join-Path (Get-Location) '.local/acceptance/stage-2'
./scripts/Verify.ps1
```

Реальный GDI-захват включается отдельно переменной `WATERMARKER_NATIVE_CAPTURE=1`.
Запускать его из обычной интерактивной сессии Windows с доступом к рабочему столу.
Проверка не сохраняет снимок без метки; в `physical-displays.json` записываются
только размеры, координаты и масштаб мониторов. В CI этот аппаратный тест пропускается.

`WaterMarker.FaultHost` — отдельный проверочный процесс, который аварийно завершается
на контрольной точке экспорта либо ожидает принудительного завершения тестом.
`WaterMarker.Stage2.Tests` проверяет восстановление после такого завершения, блокировки
файлов, конфликт имён, сохранность кодов и идемпотентность повторного восстановления.
Все операции выполняются в отдельных временных каталогах.

Восстановление удаляет временный файл, только если его путь совпадает с вычисленным
по ID операции именем рядом с назначением. Недоступный файл остаётся для повторной
попытки; пользователь получает сообщение. Отмена и переход к публикации используют
одну синхронизированную границу. Файловый код окон не содержит обработки медиа или БД;
code-behind управляет только закрытием и геометрией окна.

## Границы модулей

| Проект | Ответственность | Зависимости |
| --- | --- | --- |
| `WaterMarker.Core` | Модели, правила, контракты, сценарий экспорта | Только .NET |
| `WaterMarker.Infrastructure` | SQLite, файлы, восстановление, GDI, запуск FFmpeg/FFprobe | Core |
| `WaterMarker.Rendering` | Раскладка и прозрачный слой WPF для предпросмотра и экспорта | Core |
| `WaterMarker.App` | Представления, ViewModel, связывание реализаций с контрактами | Все три модуля |

Работа с БД и файлами не размещается в code-behind окон. Внешние процессы запускаются
с `UseShellExecute = false` и отдельными аргументами через `ArgumentList`.
Пользовательская БД и настройки находятся в `%LocalAppData%\WaterMarker`.
Временный экспорт принадлежит операции и расположен рядом с целевым файлом.

Предметное оформление находится в `WaterMarker.App/Visuals` и `Themes/Desk.xaml`.
Материалы, бумага, корпус телевизора и переплёт рисуются векторно в DIPs. Они окружают
дочерние элементы; к реальному предпросмотру не применяются текстуры, прозрачность,
блики или эффекты. Без медиа показывается один замороженный кадр аналогового шума.
Фокус и стандартное клавиатурное управление сохраняются в шаблонах полей и кнопок;
пружинящий отклик печати учитывает настройку анимаций Windows.

По уточнению интерфейса главное окно фиксировано: 1120×680 DIPs, без изменения размера
при импорте. При первом показе оно при необходимости уменьшается до рабочей области,
а сцена равномерно масштабируется вниз. `JournalWindow` — отдельное немодальное окно
с тем же ViewModel и журналом; при Screenshot оно скрывается вместе с главным окном.
`TelevisionFormats` выбирает пресет с наибольшей заполненной площадью из 1:1, 4:3,
3:4, 16:9 и 9:16. `TelevisionHost` вписывает корпус в постоянную область; пропорциональные
отступы `TelevisionCase` сохраняют тот же формат экрана. `Stretch.Uniform` не обрезает
медиа и даёт полосы только для источника, не совпадающего с выбранным форматом.
Drag-and-drop принимает один PNG/JPEG/MP4/MOV/MKV и использует обычный сценарий загрузки.

По отдельному запросу пользователя в текущую итерацию добавлен рабочий путь видео для
проверки реального прогресса; это не означает завершение этапа 3. `VideoTools` читает
длительность основного потока через FFprobe до экспорта. FFmpeg запускается с
[`-progress pipe:1`](https://ffmpeg.org/ffmpeg.html#Advanced-options) и `-stats_period 0.25`;
`out_time_us` нормализуется по длительности видео, отрицательные и откатывающиеся значения
отбрасываются. До успешной публикации шкала ограничена 99.9%, подпись — 99%.
Прозрачный PNG-слой передаётся FFmpeg через stdin, без вспомогательного файла на диске.
Экспорт использует общий `ExportService`, журнал, Cancel и границу Publishing.

`VideoProgressWindow` показывается через `ShowDialog`, обновляется в UI-потоке и
дожидается остановки процесса при Cancel/закрытии. `VideoProgressViewModel` измеряет
время монотонным `TimeProvider`; `docs/PROMPTS.md` встроен как ресурс сборки. После
каждой фразы добавляется многоточие; через 7 секунд выбирается случайная другая фраза.
Список содержит 25 исходных фраз и 25 новых. Жёлтая шкала имеет утопленную рамку,
объёмную заливку и верхний блик. Данные прогресса — обработанная длительность, не байты.

Весь штамп находится внутри шаблона одной кнопки. Hover умножает RGB материалов
на 1.15 с ограничением 255, сохраняя непрозрачность. SaveFile использует последнюю
подтверждённую папку сохранения, затем папку реального исходника; для Screenshot без
предыдущего выбора — Documents. `save-location.json` хранится рядом с пользовательской
БД; повреждение настроек не мешает экспорту.

## Цикл изменения

1. Выбрать проверяемый сценарий и критерий приёмки из раздела «Этапы разработки» ниже.
2. Внести минимальное законченное изменение. Git ведёт пользователь: создание веток,
   индекс, коммиты, слияние и публикацию помощник не выполняет.
3. Добавить проверки правил и отказов, затронутых изменением; выполнить `scripts/Verify.ps1`.
4. Проверить интерфейс и медиа вручную там, где сборка и автоматические тесты не доказывают результат.
5. Передать пользователю описание изменений и результаты проверок. Перед своим
   коммитом пользователь проверяет diff, индекс и список отслеживаемых файлов.

CI повторяет сборку Release с предупреждениями как ошибками, проверку форматирования
и запуск добавленных в решение тестов. Отсутствие проектов тестов выводится явно.
Видео и несколько физических мониторов требуют отдельных проверок приёмки.

План этапов и критерии приёмки ведутся в этом документе. Сам файл ТЗ, рабочие
заметки, приватные материалы и результаты приёмки хранятся локально и не публикуются.
README содержит инструкции по продукту, без отчётов о разработке.

## Этапы разработки

Критерии составлены по согласованному ТЗ. Подготовка репозитория не считается
выполнением этапа продукта. Этот раздел — единый план разработки и приёмки.

### Общие правила перехода

Этапы идут последовательно: 1 → 2 → 3. Следующий этап начинается после явного
принятия пользователем предыдущего. Завершение подтверждают сборка, автоматические
проверки и воспроизводимый протокол ручной приёмки. Если пользователь явно принимает
этап с невыполненными пунктами, зафиксировать решение; это не переводит эти критерии
в статус «пройдено» автоматически. Открытые дефекты и непроверенные пункты остаются
видны в протоколе.

Для каждого критерия протокол содержит идентификатор, сборку/коммит, среду,
исходные данные, шаги, ожидаемый и фактический результат, ссылки на доказательства.
Сохранять протоколы в `.local/acceptance/stage-N.md`; приватные медиа — в `test-data`.
Время в БД — UTC, в интерфейсе — местное с подписью `Exported at`.
Интерфейс английский, документация русская. Обработка медиа локальная.

### Этап 1. Изображения, проекты и журнал

**Результат:** законченный путь от PNG/JPEG до персональной копии с поиском по коду.

Работы: модели и контракты Core; миграции SQLite; проекты и журнал;
криптографические коды; общая раскладка и отрисовка WPF; загрузка изображения,
предпросмотр и экспорт; минимальный рабочий интерфейс с клавиатурным управлением.
Сразу заложить состояния `Rendering → Publishing → Ready`, контрольную сумму,
временный файл рядом с назначением и публикацию без перезаписи. Для `Interrupted`
коды сохраняются зарезервированными. Восстановление с имитацией сбоев принимается на этапе 2.

| ID | Проверяемый критерий приёмки |
| --- | --- |
| 1.1 | На чистой БД выбран `No project`, список проектов пуст. Создание и переименование отсекают пустые, пробельные и дублирующиеся без учёта регистра названия после trim. У проекта неизменный ID. |
| 1.2 | PNG сохраняет размеры и альфа-канал; полностью прозрачные пиксели остаются прозрачными. JPEG с EXIF-ориентацией экспортируется с правильной ориентацией в JPEG высокого качества и PNG. Хеш исходника до и после совпадает. |
| 1.3 | Поля Project, Recipient, Channel проверяются до экспорта. Есть Telegram, Discord, Email, Other; Other требует своего названия. Ошибка оставляет исходник и введённые поля. После успеха работают Open file / Open folder. |
| 1.4 | Один файл → адресат A, адресат B, снова A дают ровно три Ready-записи с попарно непересекающимися наборами кодов. Каждый код — 10 символов заданного алфавита, создан RandomNumberGenerator. Принудительная коллизия повторяет генерацию, UNIQUE SQLite не допускает дубликат. |
| 1.5 | Живой поиск по любой непрерывной части кода показывает все совпавшие копии и полный набор их кодов. DZ совпадает в любой позиции, но не с раздельными D и Z или последовательностью ZD. Одна копия выводится один раз, даже при нескольких совпавших кодах. Trim и регистр не влияют; неизвестный фрагмент даёт No matching record. Поиск глобальный, работает после перезапуска и удаления медиа. Очистка поля возвращает выбранный фильтр проекта. |
| 1.6 | Создать «Дизайн упаковки», Photo Review и экспорт без проекта. На копиях верные надписи; фильтры All projects / проект / No project дают нужные записи. Поиск кода другого проекта обходит активный фильтр. После переименования фильтр находит старые записи по ID, детали показывают прежнее название, новый экспорт печатает новое. |
| 1.7 | Выбор проекта обновляет предпросмотр. В начале экспорта фиксируются ID и название; переключение/переименование во время обработки не меняет уже запущенную копию. Предпросмотр и экспорт используют один модуль; заглушки равны настоящим кодам по длине и ширине символов. |
| 1.8 | Один пресет: сетка по всему кадру, соседние ряды смещены, наклон 30° вверх вправо; код не разрывается при переносе длинного кириллического названия. В пределах одного изображения коды не повторяются. |
| 1.9 | Для светлого/тёмного скриншота с мелким текстом и фотографии, в вариантах No project и длинного кириллического названия, проверить 1920×1080 и 1080×1920. Из каждого результата взять 5 обрезок: четыре квадранта и центр. Размеры обрезок 960×540 и 540×960 соответственно (четверть площади). Во всех читается полный код; мелкий текст исходника читаем. Сохранить обрезки и оценку читаемости. |
| 1.10 | Экспорт работает в фоне, окно отвечает на ввод. При занятом имени предлагается другое; существующий файл и исходник сохраняют хеш. В журнале новые записи выше старых, показаны проект на момент экспорта, адресат, канал, Exported at и имя копии. |

**Проверки:** unit-тесты правил названий/кодов/раскладки; интеграционные тесты
SQLite и сохранения; визуальная матрица изображений. `scripts/Verify.ps1` проходит.
**Покрывает ТЗ:** §8 п.2, п.3, п.7; часть п.1, п.5, п.6.

### Этап 2. Захват экрана, надёжность сохранения и интерфейс

**Результат:** безопасный рабочий процесс изображений и скриншотов на нескольких дисплеях.

Работы: GDI-захват замороженного рабочего стола; выбор области на одном мониторе;
физические координаты и Per Monitor V2; отмена; восстановление незавершённых
операций; инъекция отказов; окончательный визуальный стиль и доступность.

| ID | Проверяемый критерий приёмки |
| --- | --- |
| 2.1 | Screenshot скрывает главное окно и открытый журнал до снимка. Выделение на замороженном кадре становится исходником при отпускании мыши. В результате нет окон приложения и рамки. Esc возвращает прежний исходник; файл скриншота без метки на диске не появляется. |
| 2.2 | Пройти матрицу 100%, 125%, 150%, включая второй монитор слева от основного (отрицательные координаты) и пару дисплеев с разным DPI. Результат совпадает с выделенными физическими пикселями; выделение ограничено одним монитором. |
| 2.3 | На отказе записи, отмене до Publishing и закрытии во время Rendering под финальным именем нет неполного файла. Поля и исходник сохраняются при обрабатываемой ошибке. Cancel недоступен с начала публикации. |
| 2.4 | Имитировать остановку после резервирования кодов, во время записи temp, после записи Publishing, после финального rename и перед Ready. После перезапуска целый temp публикуется без перезаписи, финальный файл с правильным хешем получает Ready, остальные операции — Interrupted с удалением только собственного temp. |
| 2.5 | Если финальное имя занято чужим файлом, файл остаётся цел, операция прерывается. Publishing находится по коду с пометкой незавершённого сохранения. Interrupted не попадает в обычный список, его коды никогда не выдаются повторно. Повторный запуск восстановления идемпотентен. |
| 2.6 | Интерфейс соответствует ТЗ: зелёный фетр под стеклом, бумага параметров, корпус телевизора, кнопка-печать, разлинованный журнал. Декор не обрезает края медиа, не тонирует предпросмотр. Нет слоганов и декоративных подписей. |
| 2.7 | При 125% и 150% нет обрезанных полей/действий; Tab идёт в понятном порядке, фокус видим. Watermark доступен мышью и клавиатурой, имеет визуальный отклик. Обработка не блокирует интерфейс. |
| 2.8 | Телевизор и его экран всегда имеют формат 1:1, 4:3, 3:4, 16:9 или 9:16, выбираемый по контенту. На всех пяти совпадающих источниках полос нет. Произвольные пропорции вписываются целиком в ближайший пресет с допустимыми полосами. Загрузка и переключение контента не меняют размеры главного окна. |
| 2.9 | До загрузки — статичный серый муар аналогового отсутствия сигнала, без анимации. Один PNG/JPEG можно перетащить на телевизор; ошибочный файл, несколько файлов и попытка во время обработки не заменяют текущий исходник и поля. |
| 2.10 | Journal открывается отдельным окном, повторное нажатие активирует уже открытое. Поиск, фильтр, детали и обновление записей работают через общий ViewModel. Главное окно не изменяет размеры при открытии журнала. Кнопка снимка подписана Screenshot. |
| 2.11 | Ручка, стойка и основание штампа составляют одну кнопку. Наведение повышает яркость на 15%, нажатие даёт отклик. После проверки полей открывается Windows SaveFile: сначала папка исходника, далее последняя выбранная папка, сохраняемая между запусками. Отмена диалога не запускает экспорт. |
| 2.12 | Поиск в журнале обновляется без Enter или кнопки, с паузой 200 мс после ввода. Чтение БД не блокирует UI; результаты старого запроса не заменяют новый. Полный код также работает. Неполные сохранения доступны с пометкой; обычный список после очистки содержит только Ready. |

**Проверки:** интеграционные тесты с контролируемыми точками отказа и временной БД;
ручной протокол физических мониторов/DPI; повтор всей приёмки этапа 1.
**Покрывает ТЗ:** §8 п.1, п.5 и UI-часть п.6; требования сохранения §5.

### Этап 3. Видео, лицензии и выпуск Windows 11 x64

**Результат:** проверенный видеопроцесс от выбора момента до воспроизводимой H.264-копии,
а также лицензированная и документированная поставка для чистой Windows 11 x64.

Этап включает три связанных результата:

1. **Проверка входного видео.** Надёжно определить потоки, длительности, временные метки,
   частоту кадров, размеры, поворот, цветовой профиль и аудиодорожки. До долгого экспорта
   объяснить пользователю, если контейнер или кодеки не подходят для выбранного результата.
2. **Предпросмотр и экспорт.** Дать выбрать кадр предпросмотра; использовать одну и ту же
   неизменную раскладку кодов в кадрах ролика. Сохранить ориентацию, VFR, звук и синхронизацию.
   Проверить Cancel, восстановление после сбоев и содержимое временного/готового файла.
3. **Право и выпуск.** Выбрать лицензию WaterMarker, учесть лицензии всех прямых и
   транзитивных зависимостей, решить, поставляется ли FFmpeg отдельно пользователем или
   вместе с приложением, подготовить обязательные тексты и атрибуции. Собрать и пройти
   сценарии на чистой Windows x64.

**Порядок этапа:** сначала определить владельцев авторских прав, цель распространения
(открытый исходный код/закрытый продукт) и судьбу FFmpeg, чтобы не строить релиз на
несогласованных лицензиях. Затем закрыть видеоформаты и предпросмотр; после этого —
отказы, метаданные, документацию и чистую Windows-сборку. Уже созданные FFprobe-анализ,
базовый H.264-экспорт, модалка и отмена служат отправной точкой, но не доказывают
совместимость всей видео-матрицы и годность конкретной сборки FFmpeg для распространения.

Пользователь выбрал MIT для исходного кода WaterMarker, указав Caspian правообладателем;
стандартный текст `LICENSE` добавлен в корень (SPDX: MIT). Пользователь планирует
открытый проект с FFmpeg в комплекте; лицензирование графики и сторонних материалов
нужно уточнить по происхождению каждого элемента. Решение фиксируется с корректными
сведениями о правообладателях;
права нельзя выводить из наличия репозитория на GitHub. Отдельно составляется инвентаризация
NuGet и встроенных/поставляемых компонентов: название, версия, лицензия, источник и
требуемый текст уведомления. Итоговая `THIRD-PARTY-NOTICES.md` и оригинальные лицензии,
где это требуется их условиями, идут в исходный код и дистрибутив.

**FFmpeg — отдельное решение о поставке.** Приложение сейчас запускает внешние `ffmpeg`
и `ffprobe` и не включает их в репозиторий. Найденная в среде сборка FFmpeg 8.0.1
full_build от gyan.dev собрана с `--enable-gpl`, `--enable-version3`, `--enable-static`
и `--enable-libx264`; её `-L` сообщает GPLv3. Кодер x264 сам также требует отдельного
учёта лицензии и патентных рисков H.264. Одна строка «использует FFmpeg» сама по себе не
закрывает проверку поставки бинарников. Для релизного сценария нужно выбрать конкретную
сборку, зафиксировать её хеш, `-version`, `-buildconf`, `-L`, включённые библиотеки,
лицензии/исходники и путь получения. Если FFmpeg будет поставляться с приложением,
до сборки релиза нужна проверка совместимости выбранных условий с выбранной лицензией
WaterMarker и соблюдения всех применимых обязательств. Если он остаётся внешней
зависимостью, это ясно описывается пользователю, а версия/атрибуция фиксируются в
документации. H.264 также оценивается отдельно от авторских лицензий программ.

Пользователь выбрал открытый проект под MIT и поставку FFmpeg в комплекте. Это решение
не заменяет проверку условий конкретной GPL-сборки и не означает, что её бинарники,
соответствующие исходники и все уведомления уже подготовлены к распространению.
